# Experiment E6: ablation — the tool without OpenAPI x-access-control annotations

**Status: EXECUTED.** This ablation addresses the threat to validity that the benchmark's OpenAPI
specification carries `x-access-control` annotations which real-world APIs usually lack, and which
could give the tool an unfair advantage (see docs/DECISIONS.md D2).

| Item | Value |
|---|---|
| Date | 2026-11-21 |
| Tool | bac-scanner 1.0.0, ownership-differential oracle |
| Target | test-api vulnerable build (FLAWS=all, :3000) |
| Ground truth | test-api/ground-truth.json (234 scored cases, 20 vulnerable) |
| Ablated spec | `openapi.no-annotations.yaml` — test-api/openapi.yaml with every `x-access-control` removed (the HTTP `security` requirements are kept). Generated by stripping the 47 annotations. |

## Variants

- **Baseline (annotations):** the normal annotated spec and `cli-tool/config/example.config.yaml`. This reproduces E3.
- **Config rules, no annotations:** the ablated spec plus `ablation.config.yaml`, which supplies the same
  intended policy through configuration `accessRules` (31 rules re-encoding ownership and role restrictions),
  exactly as a tester configures an un-annotated real API (the approach used for VAmPI).
- **No policy source:** the ablated spec with the default config, which carries **no** `accessRules`. The tool
  then has no statement of the intended policy from either the spec or the config.

## Interpretation

- The authorization policy that defines BOLA and BFLA (who owns which object, which role may call which
  function) is **not observable from HTTP traffic**. The tool must be told it.
- With the annotations removed and nothing supplied in their place ("No policy source"), the tool generates
  no cross-user or cross-role tests and detects **0 of 14** BOLA/BFLA cases. Crucially it does not guess:
  precision stays 1.000 and it raises **no false positives**. It still finds the 6 authentication/JWT flaws,
  because those derive from the spec's `security` requirement rather than from `x-access-control`.
- When the same policy is instead supplied through configuration ("Config rules, no annotations"), detection
  is **fully restored** to the baseline (20/20, precision and recall 1.000).
- Therefore the tool does not depend specifically on OpenAPI `x-access-control` annotations; it depends on a
  declared policy source, which may be the specification **or** the configuration. The benchmark's annotations
  are a convenience, not the reason the tool succeeds. This bounds the "annotation advantage" threat: the
  advantage is in having a machine-readable policy at all, and a human tester provides the same via config,
  as demonstrated on VAmPI (E5).
